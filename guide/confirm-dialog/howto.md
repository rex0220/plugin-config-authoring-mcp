# 確認ダイアログ: 作業手順

確認ダイアログプラグイン（Ver.6 以降）の設定を、要件から作る・今の設定を直すときの手順です。ツールは `cdlg_*`。**kintone には何も書きません。** 作るのは作業フォルダーのファイルで、設定画面への読み込みと保存は利用者が行います。

確認ダイアログは、**レコードの保存・プロセス管理のアクションの実行・ボタンのクリックのときに、条件の式が真のダイアログを順に出す**プラグインです。保存とアクションでは、キャンセルすると止まり（保存・実行されない）、OK で進んだ後に通知を出せます。

## 始める前に

1. `cdlg_status` で、プラグインの zip と kintone の接続が読めるかを確かめる。`problem` や `not-configured` があれば、利用者に設定を頼む（zip の場所、接続のファイル）。自分で直そうとしない。
   - **接続の profile を確かめる**。`kintone.profileSelection` が `locked` なら、使う profile は起動の設定で 1 つに決まっている（`profile` の引数は書かない）。
   - `tool-selectable` で `profiles` が 2 つ以上あるときは、**kintone を読むツール（`cdlg_fields` / `cdlg_pull` / `cdlg_check` / `cdlg_try` / `cdlg_export`）を呼ぶ前に、どの profile を使うかを利用者に確かめる**。名前から環境を推し量らない。
2. 作る前に、利用者の頼みが確認ダイアログに向いているかを確かめる。
   - **向いている**: 保存の前に内容を見せて確かめさせる、条件に合うときだけ注意を出す、条件に合うときは保存・アクションを止める（アイコン error のダイアログ）、アクションの実行の前に確かめる、保存の後に通知を出す、詳細・追加・編集の画面のボタンでレコードの概要（HTML）を見せる。
   - **向いていない**: 値を計算して入れる（計算式プラグイン）、項目ごとに入力の誤りを出す・必須にする（項目検証プラグイン）、ログインユーザーの所属（組織・グループ）で出し分ける（`UINFO` などは使えない）、一覧の画面にボタンを出す、ダイアログの中で値を入力させる。向いていなければ、作る前にそう伝える。

## 新しく作る

1. **項目とプロセス管理を確かめる**。`cdlg_fields`（`app` = アプリの番号、`preview: true`）で、項目コード・タイプ・ラベル・テーブル・選択肢（`options`）と、プロセス管理（`process`: 有効か・ステータス・アクション）を読む。項目コード・選択肢の名前・アクションの名前は推測しない。
   - `process.enabled` が `false`（プロセス管理が無効）のアプリでは、プロセスアクションの行は動かない（検査が warning を出す）。作る前に利用者に伝える。
   - `processNote` が出たら、そのまま読む（読めなかった / 言語ごとの名前が付いている）。
2. **設定ファイルを作る**。`cdlg_new`（`file` と `app`）。行は無い状態で始まる。
3. **行を足す**。1 行が 1 つの設定（ダイアログ名）。`cdlg_read` の `key: "new"` で行の雛形（保存イベント）を取り、`name`・`event` と、その対象イベントの設定（`save` / `actions` / `buttons`）、ステップ（`steps`）を書いて、`cdlg_update` の `addRow` で足す。書き方は `cdlg_docs` の `spec`。
4. **検査する**。`cdlg_check`。`error` を直して、もう一度検査する。指摘はそのまま利用者に伝える。
5. **レコードと場面を当てて確かめる**。`cdlg_try`（次の節）。検査は式の文法と項目があるかまでしか見ない。**ダイアログが思ったとおりに出るかは、ここで確かめる**。
6. **取り込み用のファイルを作る**。`cdlg_export`（`expectedDigest` は `cdlg_check` か `cdlg_try` が返した設定ファイルの digest）。返った `nextSteps` を利用者に伝える。

## レコードと場面を当てて確かめる（`cdlg_try`）

- **場面（`scenes`）を必ず書く**。設定した対象イベントに合わせる。10 個まで。
  - 保存: `{ "event": "update" }`（編集の画面の保存）、`{ "event": "create" }`（追加の画面の保存）、`{ "event": "index" }`（一覧での編集の保存）
  - アクション: `{ "event": "process", "action": { "name": "承認", "from": "処理中", "to": "完了" } }`（名前は `cdlg_fields` の `process.actions` のとおりに。既定の名称）
  - ボタン: `{ "event": "button", "screen": "detail" }`（`detail` = 詳細、`create` = 追加、`update` = 編集）
  - 言語ごとの式・ボタン名を確かめるときは `"lang": "en"`（`ja` / `en` / `zh`）、モバイルは `"mobile": true`。
- 利用者に、確かめるレコードを聞く。**ダイアログが出るはずのレコードと、出ないはずのレコードの両方**（レコード番号 `ids`、または条件 `query`）。分からなければ `query: "order by $id desc"` で新しい順の 20 件までを当てる（`query` に `limit` / `offset` は書かない）。
- 空の値・境目の値（ちょうど 100 万、今日の日付など）は、`records` に自分でレコードを書いて当てる（kintone の REST の形。`{ "項目コード": { "type": "NUMBER", "value": "1000000" } }`。テーブルは `{ "type": "SUBTABLE", "value": [{ "id": "1", "value": { 子のコード: { type, value } } }] }`）。
- **追加の画面（`create`）は、`records` に `$id` の無いレコードを書いて当てる**。`ids`・`query` で読んだレコードは `$id` を持つので、`IF($id, …)` のような式が更新の側になる。
- **条件を書く前に、項目の値の形や式の結果を見たいとき**は `probes` を使う（`probes: [{ "formula": "担当者" }, { "formula": "MIN(数量)<=0" }]`。設定に入れずに、式の値だけが、レコード × 場面ごとに返る）。**確かめるための設定ファイルを別に作らない**。設定ファイルが空（行なし）でも使える（`scenes` は要る。保存の式なら `[{ "event": "update" }]`）。
- `status: "no-records"` は、条件に合うレコードが無かった（誤りではない）。`query` を見直すか、`records` に自分で書いて当てる。
- 結果の読み方は `spec` の「模擬の結果」。見る所:
  - `dialogs` の並び（どの行の何番目のステップか）と、`title`・`text`・ボタンの字（`ok` / `cancel`）が、利用者の期待と合うか。出ないはずのレコードで `dialogs` が空か。
  - `onCancel`（そこでキャンセルしたときの結果）と、`notices`（全部 OK を押したときの通知）。
  - `errors`（評価できなかった式。**レコード画面では、その部分は出ないだけで、エラーの知らせも出ない**）。
- 合わなければ式を直し、`cdlg_check` → `cdlg_try` をやり直す。期待と合ったことを利用者に伝える（どのレコード・どの場面で確かめたかも）。
- 確かめられないこと: 画面での見え方（置き場所・アイコンの絵・共通 CSS）、ログインユーザーに依る式（`LOGIN_CODE()` はツールでは仮の利用者のコード、`LOGIN_NAME()` は空になる。`spec` の「ログインユーザー」）、一覧での編集の保存のときの計算の項目の値（一覧に置いてあると空になる。`spec` の「一覧での編集の保存」）、値を書き換える関数（`FSET` など。ある式は模擬しない）、他の利用者の更新の確かめ、明日以降の日付での動き。これらは利用者に、保存の後に画面で確かめてもらう。

## 今の設定を直す

1. **今の設定を設定ファイルにする**。道は 2 つ。
   - `cdlg_pull`（`file` と `app`）で、アプリから読む。読むのは動作テスト環境の設定（設定画面が読むものと同じ。運用環境なら `preview: false`）。**使えるのは、kintone の API ラボの機能（「アプリに追加されているプラグインの設定情報を取得または更新する REST API」）を cybozu.com 共通管理者が有効にしている環境だけ**。`kintone-error` が返ったら、返った `hint` を利用者に伝えて、下の道に切り替える（何度も試さない）。`no-config` は、まだ設定を保存していない（「新しく作る」へ）。
   - 利用者に、設定画面の「設定をダウンロード」で今の設定をファイルに出して、作業フォルダーの直下に置いてもらう。`cdlg_files` でそのファイルを確かめ、`cdlg_new` の `from` に渡して設定ファイルにする（元のファイルは残る）。
2. `cdlg_read` で要約と行を読み、直す所を利用者と確かめてから `cdlg_update` で直す。ステップを 1 つ足す・直すときは、行を読み、`steps` の並びを直して `patchRow` で入れる（並びは丸ごと入れ替わる）。
3. `cdlg_diff` で、直す前の設定ファイルとの差を確かめる（直す前のものを別の名前で、もう一度 `cdlg_pull` か `cdlg_new` の `from` から作っておくと比べられる）。
4. `cdlg_check` → `cdlg_try` → `cdlg_export`。今の設定を写した設定ファイルなので、取り込みは「全置換」でよい。ただし、読んで（ダウンロードして）から取り込むまでの間に設定画面で保存された変更は、全置換で消える。間が空いたら読み直すか、「一部置換」で直した行だけを取り込んでもらう。

## 直すときの決まり

- `cdlg_*` が読むのは、確認ダイアログの設定ファイルだけ。ほかのプラグインのツールで作った設定ファイルを渡すと `other-plugin` で止まる。
- 設定ファイルに知らないキーを書くと検査で止まる（`key.unknown`）。キーの名前は `spec` のとおりに。
- `cdlg_update` は、`cdlg_read` で読んだ digest を `expectedDigest` に渡す。`conflict` が返ったら、読み直してからやり直す。ほかのツールでファイルを書き換えない。
- 行を足す・消す・動かすと、行のキーは位置で振り直る。続けて直すときは、返った `rows` のキーを使う。
- **行の並びとステップの並びには意味がある**（レコード画面は、上の行から、行の中は上のステップから、条件が真のものを順に出す）。足すときは、どこに入れるかを考える。
- アクションの名前・ステータスの名前は推測しない。`cdlg_fields` の `process` で確かめる（読めなければ、今の設定の値を使うか、利用者に聞く）。
- 使わなくなった設定は、行を消すか、行の `state` を `false` にする（設定は残る）。どちらにするかは利用者に聞く。
- 値を書き換える関数（`FSET` など）は、利用者に頼まれたときだけ書く。書いたら、保存・アクションのときにレコードの値が変わることを必ず伝える（検査が warning を出す）。

## 最後に必ず伝えること

- kintone には何も書いていない。反映は、設定画面で「設定をアップロード」→ 取り込み方（**全置換** / **一部置換** / **追加**）→「保存する」（運用環境に反映）。**取り込みの画面は、最初「全置換」が選ばれている**。新しく作った設定ファイル（今の設定を写していない）を全置換で取り込むと、今あるダイアログの行が全部消えるので、「追加」か「一部置換」を選ぶように必ず伝える。
  - 全置換: 今の行を全部ファイルの行に置き換える。**ファイルに無い今の行は消える**。今の設定を写して作ったファイルならこちら。
  - 追加: チェックした行を表の末尾に足す（最初は全部にチェック）。新しく作った行を足すならこちら。同じダイアログ名の行が今の設定にあっても、その名前のまま足される（同じ名前の行が 2 つになる。置き換えたいなら一部置換）。
  - 一部置換: ファイルの行ごとに、置き換える今の行を選ぶ（同じダイアログ名の行が最初に選ばれている。選ばない行は取り込まれない）。直した行だけを入れるならこちら。
  - 今の設定を写したか分からないときは、それぞれの場合を書く。
- 行の外の設定（`common`。プラグイン有効・NOTE・説明・共通CSS・通知秒数・メニュー表示）は、**設定ファイルに書いたものだけ**がファイルに入る。全置換では、入っているものがファイルの値に置き換わる。一部置換・追加では、取り込みの画面の「共通の設定」でチェックした群だけが置き換わる（**最初はどれもチェックが外れている**）。`cdlg_export` の `nextSteps` に、ファイルに何が入っているかが出るので、そのまま伝える。
- 既存のレコードの値は変わらない。ダイアログは、保存（とアプリの更新）の後、レコードの保存・アクションの実行・ボタンのクリックのときに出る。
- アクション名・ステータス名は名前で覚えている。**プロセス管理で名前を変えたら、設定を直す**（`cdlg_check` が「アプリのプロセス管理に無いアクション」を warning で知らせる）。言語ごとの名前を付けているアプリでは、名前を変えた後に設定画面を開いて保存する。
- `cdlg_try` で確かめたレコード・場面と結果。確かめていないこと（画面での見え方、ログインユーザーに依る式、値を書き換える関数）。
- warning の指摘があれば、消さずに伝える。
